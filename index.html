Практическая работа 4. Выбор стиля взаимодействия с API

Взаимодействуйте с четырьмя сервисами, имитирующими ML-инференс: REST сразу возвращает предсказание, gRPC принимает типизированный пакет транзакций, WebSocket обрабатывает поток измерений в одном соединении, а event-driven API передаёт задание отдельному обработчику.

Модели используют простые детерминированные правила. Цель — исследовать протоколы: что отправляет клиент, когда получает ответ и где проходит граница между сервисами.

Инструкция по установке Docker, Compose, запуску и поиску неисправностей находится в README репозитория.

Что понадобится

  • Docker Engine с Compose plugin или Docker Desktop; терминал macOS, Linux или WSL.
  • cURL для HTTP-запросов.
  • grpcurl для gRPC (Homebrew: brew install grpcurl).
  • websocat для WebSocket (Homebrew: brew install websocat).
  • NATS CLI для изучения брокера; CLI подключается к локальному NATS на 127.0.0.1:4222.

Подготовка стенда

Переключитесь на ветку seminar/04-api-interaction-styles, скопируйте .env.example в .env, оставьте HOSTING_TYPE=local и запустите из корня репозитория:

docker compose build
docker compose up -d
docker compose ps

Локальные адреса: REST — http://127.0.0.1:8011/v1/predict; gRPC — 127.0.0.1:8012; WebSocket — ws://127.0.0.1:8013/v1/live; event API — http://127.0.0.1:8014/v1/jobs и /v1/jobs/{job_id}.

На серверном стенде используйте https://seminar04.dataprosvet.ru/rest, wss://seminar04.dataprosvet.ru/stream, https://seminar04.dataprosvet.ru/events. gRPC — seminar04.dataprosvet.ru:443, метод /seminar04.v1.TransactionInference/PredictBatch. Узнайте у преподавателя, включена ли Basic Auth. NATS доступен только локально и не проксируется через Caddy.

1. REST: немедленный ответ

Передайте срок обслуживания клиента, месячные расходы и число обращений в поддержку. Ответ содержит оценку риска risk_score и метку risk_label.

Успешный запрос

curl -i -X POST http://127.0.0.1:8011/v1/predict \
  -H 'Content-Type: application/json' \
  -d '{"tenure_months":18,"monthly_spend":240.5,"support_tickets":2}'

Путь на хостинге: POST https://seminar04.dataprosvet.ru/rest/v1/predict. Запишите HTTP-код и оба поля результата. Предсказание приходит в ответе на тот же вызов.

Запрос с ошибкой

curl -i -X POST http://127.0.0.1:8011/v1/predict \
  -H 'Content-Type: application/json' \
  -d '{"tenure_months":18,"support_tickets":2}'

Обязательное поле monthly_spend пропущено. Запишите статус и тело ошибки. Документация: http://127.0.0.1:8011/docs локально и https://seminar04.dataprosvet.ru/rest/docs на хостинге.

2. gRPC: типизированный пакет

gRPC использует HTTP/2 и protobuf-схемы. Reflection позволяет grpcurl обнаружить метод без скачивания proto-файла.

Успешный запрос

grpcurl -plaintext 127.0.0.1:8012 list
grpcurl -plaintext 127.0.0.1:8012 describe seminar04.v1.TransactionInference
grpcurl -plaintext -d '{"transactions":[{"id":"tx-1","amount":125.5,"international":false,"merchant_risk":0.2},{"id":"tx-2","amount":980,"international":true,"merchant_risk":0.8}]}' \
  127.0.0.1:8012 seminar04.v1.TransactionInference/PredictBatch

В predictions сопоставьте каждый результат с идентификатором транзакции. На сервере используйте TLS: grpcurl -d '{"transactions":[{"id":"tx-1","amount":125.5,"international":false,"merchant_risk":0.2}]}' seminar04.dataprosvet.ru:443 seminar04.v1.TransactionInference/PredictBatch.

Запрос с ошибкой

grpcurl -plaintext -d '{"transactions":[{"amount":125.5,"international":false,"merchant_risk":0.2}]}' \
  127.0.0.1:8012 seminar04.v1.TransactionInference/PredictBatch

У обязательного поля id нет значения. Запишите gRPC status и сообщение; сравните с HTTP validation error REST.

3. WebSocket: поток предсказаний

Сервис принимает измерения температуры, вибрации и оборотов двигателя. Отправьте несколько сообщений в одном открытом соединении и получите оценку anomaly_score и флаг anomaly для каждого.

Успешные сообщения в одном соединении

websocat -t ws://127.0.0.1:8013/v1/live

Введите по одной строке, нажимая Enter после каждой:

{"temperature":65,"vibration":0.12,"rpm":1400}
{"temperature":112,"vibration":0.91,"rpm":2800}

После каждой строки найдите ответ с anomaly_score и anomaly. На хостинге подключитесь командой websocat -t wss://seminar04.dataprosvet.ru/stream/v1/live.

Сообщение с ошибкой

Не закрывая локальный сеанс, введите:

{"temperature":65,"rpm":1400}

Поле vibration пропущено. Сервис возвращает сообщение {"error":"invalid_telemetry","detail":"..."} и оставляет соединение открытым. Введите ещё одно корректное сообщение, получите новое предсказание и завершите сеанс Ctrl+D. Сравните задержку ответа в уже открытом WebSocket-соединении с REST-запросом.

4. Event-driven: задание для отдельного worker

HTTP endpoint принимает пакет и отвечает 202 Accepted с job_id. Затем event API публикует запрос в NATS JetStream. Отдельный worker выполняет нормализацию и inference и публикует результат. Код 202 означает, что задание принято, но ещё не обязательно завершено.

Успешное задание и получение статуса

curl -i -X POST http://127.0.0.1:8014/v1/jobs \
  -H 'Content-Type: application/json' \
  -d '{"records":[{"customer_id":"c-1","monthly_usage":42,"support_tickets":1},{"customer_id":"c-2","monthly_usage":105,"support_tickets":4}]}'

Сохраните job_id из ответа и подставьте его в команду:

JOB_ID='вставьте-job_id-из-ответа'
curl -i "http://127.0.0.1:8014/v1/jobs/$JOB_ID"

Если статус ещё pending, повторите GET через короткий интервал. После завершения сохраните результаты. На хостинге: POST https://seminar04.dataprosvet.ru/events/v1/jobs, затем GET /events/v1/jobs/{job_id}.

Неверное тело

curl -i -X POST http://127.0.0.1:8014/v1/jobs \
  -H 'Content-Type: application/json' \
  -d '{}'

В теле нет обязательного списка records; запишите ошибку валидации.

Посмотрите события в локальном NATS

nats --server nats://127.0.0.1:4222 stream ls
nats --server nats://127.0.0.1:4222 stream view INFERENCE --subject 'inference.request.>'
nats --server nats://127.0.0.1:4222 stream view INFERENCE --subject 'inference.result.>'

Найдите request и result события с subject inference.request.<job_id> и inference.result.<job_id>. Сопоставьте идентификатор в HTTP-ответе, NATS и GET-результате. Просмотр потока интерактивный. Прямой просмотр брокера доступен только в локальном Compose; NATS не публикуется через Caddy.

Сравните стили

Заполните таблицу. Для каждого сценария объясните, требуется ли немедленный ответ, допустима ли обработка в фоне и нужно ли постоянное соединение.

СценарийСтильОбоснование
Бизнес-сервис: сразу показать данные клиента
ETL: принять пакет и сообщить о готовности после фоновой обработки
ML: оценивать поток телеметрии без повторного соединения

Объясните, почему HTTP endpoint с ответом 202 сам по себе ещё не образует event-driven архитектуру. Опишите роль брокера и отдельного worker.
