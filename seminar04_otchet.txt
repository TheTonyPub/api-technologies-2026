2. Таблица выбора стиля
Сценарий: Бизнес-сервис, сразу показать данные клиента
Стиль: REST
Почему: ответ нужен сразу на один запрос, фоновая обработка не нужна, держать соединение открытым незачем.

Сценарий: ETL, принять пакет и сообщить о готовности после фоновой обработки
Стиль: Event-driven
Почему: ответ сразу не нужен, обработка идёт в фоне отдельным worker, результат забираем позже по job_id, постоянное соединение не нужно.

Сценарий: ML, оценивать поток телеметрии без повторного соединения
Стиль: WebSocket (или gRPC bidi)
Почему: данные идут всё время, ответ нужен на каждое сообщение, соединение открываем один раз.


3. Наблюдения
Время ответа. REST занял 0.93 секунды (замер curl). Каждый rest запрос это отдельный вызов со своим соединением. В WebSocket и gRPC bidi ответы приходили почти сразу после отправки строки, потому что соединение уже открыто.

Unary: один запрос, один ответ со списком predictions.
Server streaming: один запрос, но ответов два, каждый отдельным сообщением со своим id.
Client streaming: я отправил две транзакции, а ответ пришёл один (transaction_count 2, average_risk 0.53, high_risk_count 1), и только после того, как поток закрылся.
Bidi: ответ на каждую транзакцию приходил сразу, ещё до конца ввода.

Корреляция. В unary, server streaming и bidi оценки одинаковые: tx-1 это 0.213 low, tx-2 это 0.848 high. Так и должно быть, везде используется одна и та же оценка риска. Ответы можно сопоставить по id транзакции. В event API результаты сопоставляются по job_id и customer_id.

Ошибки.
REST и event API: код 422 и тело detail с указанием, какого поля нет.
gRPC: статус InvalidArgument и короткое сообщение "transaction id must not be empty".
WebSocket: пришло сообщение invalid_telemetry, а соединение осталось открытым. Я отправил после ошибки нормальное сообщение и получил обычный ответ.
