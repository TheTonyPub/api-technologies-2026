## 2. Границы системы

Внешние системы, их мы не проектируем:
- **СПАРК Интерфакс**, источник данных. Его настоящий API работает по SOAP/XML, описание поставщика: [spark-interfax.ru/integration](https://spark-interfax.ru/integration).
- **CRM** и **АБС**, потребители. Ходят к нам только через API Gateway.
- **Аналитический контур** (DWH/BI), получает данные по ETL.

Сервисы, которые проектируем мы: API Gateway, Client Info Service, Group Companies Service, Scoring Service, ML Model, Loader, Enrichment Service, Data Store (PostgreSQL), Cache (Redis).

## 3. Все взаимодействия по контейнерной диаграмме

### 3.1. REST (на каждое есть свой OpenAPI-контракт)

| # | Кто вызывает | Кого | Зачем | Что отправляет → что получает | Протокол | Контракт |
|---|---|---|---|---|---|---|
| R1 | CRM | API Gateway | Данные клиента, группа, скоринг для сотрудника банка | ИНН (и `onlyBankClients` для группы) → данные компании, состав группы или скоринг | REST/JSON | [api-gateway](contracts/api-gateway/openapi.yaml) |
| R2 | АБС | API Gateway | То же для банковских процессов | то же, что в R1 | REST/JSON | [api-gateway](contracts/api-gateway/openapi.yaml) |
| R3 | API Gateway | Client Info Service | Данные о клиенте по ИНН | ИНН → данные компании | REST/JSON | [client-info-service](contracts/client-info-service/openapi.yaml) |
| R4 | API Gateway | Group Companies Service | Все клиенты группы компаний | ИНН, фильтр → состав группы | REST/JSON | [group-companies-service](contracts/group-companies-service/openapi.yaml) |
| R5 | API Gateway | Scoring Service | Скоринг потенциального клиента | ИНН → вероятность и версия модели | REST/JSON | [scoring-service](contracts/scoring-service/openapi.yaml) |
| R6 | Scoring Service | ML Model | Посчитать вероятность | признаки компании → вероятность | REST/JSON | [ml-model](contracts/ml-model/openapi.yaml) |

CRM и АБС пользуются одним и тем же API, поэтому контракт у них общий (`api-gateway`). Сам Gateway бизнес-логики не содержит: проверяет токен, передаёт запрос дальше, следит за временем ожидания и приводит ошибки к одному виду.

### 3.2. Всё остальное (не REST, OpenAPI не нужен)

| # | Кто → кому | Протокол | Что передаётся и зачем |
|---|---|---|---|
| N1 | Loader → СПАРК Интерфакс | SOAP/XML | Loader отправляет запрос по компании, получает XML с данными. **Это внешний сервис.** Настоящий контракт смотрим у поставщика ([ссылка](https://spark-interfax.ru/integration)), конкретные методы и схемы здесь не пересказываем и своими не подменяем. |
| N2 | Loader → Data Store | SQL | Записывает новые версии записей (SCD2) |
| N3 | Enrichment → Data Store | SQL | Читает историю, пишет актуальный срез |
| N4 | Enrichment → Cache | Redis | Кладёт свежие данные с TTL (прогрев кэша) |
| N5 | Enrichment → Аналитический контур | ETL | Передаёт исторические данные и актуальный срез |
| N6 | Client Info Service → Cache | Redis | Ищет данные по ИНН в кэше |
| N7 | Client Info Service → Data Store | SQL | Читает актуальный срез, если в кэше пусто |
| N8 | Group Companies Service → Data Store | SQL | Читает актуальный срез |
| N9 | Scoring Service → Data Store | SQL | Читает актуальный срез |

Загрузка из СПАРК, обогащение, прогрев кэша и ETL идут в фоне по инициативе самой платформы, у них нет REST-входа. Мы предполагаем, что они запускаются по расписанию. На диаграмме запуск не показан, это допущение.

## 4. Операции

Общее для всех контрактов:
- версия в пути (`/v1`);
- данные читаем через `GET`;
- даты в формате RFC 3339, время UTC;
- ИНН это ровно 10 цифр;
- заголовок `X-Request-Id` (UUID) можно передать, а если нет, сервис создаст свой. В ответе он есть всегда;
- ошибки везде выглядят одинаково: `code`, `message`, `traceId` и необязательный `details` для ответа 400.

### 4.1. API Gateway (вызывают CRM и АБС)

Доступ по токену: `Authorization: Bearer <токен>`. Токены в контракт не пишем.

| Операция | Метод и путь | Параметры | Успех | Ошибки |
|---|---|---|---|---|
| `getCompanyByInn` | `GET /v1/companies/{inn}` | `inn` в пути; `X-Request-Id` по желанию | 200, `CompanyInfo` | 400, 401, 404, 500, 503, 504 |
| `getCompanyGroup` | `GET /v1/companies/{inn}/group` | `inn` в пути; `onlyBankClients` (по умолчанию `false`) | 200, `CompanyGroup` | 400, 401, 404, 500, 503, 504 |
| `getCompanyScoring` | `GET /v1/companies/{inn}/scoring` | `inn` в пути | 200, `CompanyScoring` | 400, 401, 404, 500, 503, 504 |

### 4.2. Внутренние сервисы (вызывает API Gateway)

| Сервис | Метод и путь | Успех | Ошибки |
|---|---|---|---|
| Client Info Service | `GET /v1/companies/{inn}` | 200, `CompanyInfo` | 400, 404, 500, 503 |
| Group Companies Service | `GET /v1/companies/{inn}/group` | 200, `CompanyGroup` | 400, 404, 500, 503 |
| Scoring Service | `GET /v1/companies/{inn}/scoring` | 200, `CompanyScoring` | 400, 404, 500, 503, 504 |

### 4.3. ML Model (вызывает Scoring Service)

| Операция | Метод и путь | Тело запроса | Успех | Ошибки |
|---|---|---|---|---|
| `createPrediction` | `POST /v1/predictions` | `features`: `companyAgeMonths`, `mainActivityCode`, `status`, `groupSize`, `groupBankClientsCount` (все обязательные) | 200, `probability`, `modelVersion`, `predictedAt` | 400, 500, 503 |

Здесь `POST`, потому что признаки идут в теле запроса. Модель ничего не сохраняет и ничего не создаёт, поэтому успешный ответ 200, а не 201.

### 4.4. Ошибки

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `INVALID_REQUEST` | ИНН не из 10 цифр, значение признака вне диапазона |
| 401 | `UNAUTHORIZED` | нет токена или он недействителен (только Gateway) |
| 404 | `COMPANY_NOT_FOUND` | ИНН нет в актуальном срезе |
| 500 | `INTERNAL_ERROR` | внутренняя ошибка |
| 503 | `SERVICE_UNAVAILABLE` | недоступны база, кэш, другой сервис или модель |
| 504 | `UPSTREAM_TIMEOUT` | нижестоящий сервис или модель не ответили вовремя |

Gateway превращает ошибки нижних сервисов в такой же вид. Подробности вроде текста SQL-запроса или стека наружу не отдаются.

### 4.5. Связь с C4

| Связь на контейнерной диаграмме | Операция |
|---|---|
| CRM → API Gateway, АБС → API Gateway | `getCompanyByInn`, `getCompanyGroup`, `getCompanyScoring` |
| API Gateway → Client Info Service | `GET /v1/companies/{inn}` |
| API Gateway → Group Companies Service | `GET /v1/companies/{inn}/group` |
| API Gateway → Scoring Service | `GET /v1/companies/{inn}/scoring` |
| Scoring Service → ML Model | `POST /v1/predictions` |

## 5. Что важно по кейсу СПАРК

- **Актуальный срез и SCD2.** Через REST отдаём только актуальный срез. История SCD2 нужна самой платформе и уходит в аналитический контур по ETL (N5). Отдельной операции «история» нет, кейс её не просит.
- **Свежесть данных.** В каждом ответе есть `dataAsOf`, момент, на который собран срез. Срез обновляет Enrichment после загрузки. По `dataAsOf` клиент сам видит, насколько данные свежие.
- **Кэш.** Кэш использует только Client Info Service (сначала ищет в кэше, потом в базе). Кэш хранит редко меняющиеся данные с ограниченным временем жизни (TTL), Enrichment его прогревает. Из-за кэша данные могут отставать, но не дольше, чем TTL. Конкретное значение TTL пока не выбрано.
- **10 секунд на загрузку одного клиента.** Это про фоновую загрузку, а не про REST. Загружать данные по запросу мы не будем: 10 секунд больше, чем 1 секунда на ответ. Если ИНН в срезе нет, клиент получит 404 и может повторить запрос позже, когда Loader загрузит компанию. Асинхронную задачу и статус загрузки не добавляли, кейс этого не просит.
- **Ответ за 1 секунду.** Это требование проекта, замеров нет. Для себя разложили так: Gateway до 100 мс, сервисы до 700 мс, ML Model до 400 мс (входит в время Scoring Service). Всё это наши допущения. Если время вышло, клиент получает 503 или 504, а не устаревшие или неполные данные.
- **Скоринг.** Считается сразу при запросе и нигде не сохраняется, поэтому это `GET`.
- **Группа компаний.** Ищем по ИНН любой компании из группы. Если компания есть, но группы нет, возвращаем 200 и пустой список. Фильтр `onlyBankClients` нужен, потому что кейс просит именно клиентов группы, а не всех её участников.
- **Пути и СПАРК.** Пути вида `/v1/companies/...` придуманы для нашей платформы, это не API СПАРК. Контракт СПАРК мы не пишем и своим не подменяем.

## 6. Допущения

1. Loader запускается по расписанию (на диаграмме запуск не показан).
2. Enrichment собирает актуальный срез после каждого цикла загрузки. Как часто, пока не решено, в контрактах этого нет.
3. Значение TTL кэша и допустимое отставание среза выбираются при реализации. В контрактах свежесть показывает `dataAsOf`.
4. Время ответа по сервисам (пункт 5) это наши допущения.
5. Поля `CompanyInfo` (ОГРН, КПП, статус, адрес, ОКВЭД и другие) и признаки для ML придуманы для учебного контракта, это не список полей СПАРК. `isBankClient` берётся из обогащения внутренними данными банка.
6. Группа не больше 500 компаний, поэтому постраничной выдачи нет.
7. Доступ между внутренними сервисами обеспечивается сетью и инфраструктурой, в контрактах не описан.
8. Поддерживаются только ИНН юридических лиц (10 цифр), ИП (12 цифр) не входят.
9. ИНН, ОГРН, названия, адреса и все значения в примерах выдуманные, контрольные суммы не проверяли.
