## 2. Границы REST API

* **Внешние потребители:**
  * **Клиент банка** — косвенный потребитель, инициирует транзакции через интерфейс банка.
  * **Команда аналитиков** — внутренние пользователи, поставляющие новые версии ML-моделей.
* **Внешние системы:**
  * **АБС (Автоматизированная банковская система)** — главный источник событий транзакций и получатель итоговых вердиктов.
  * **Внешние источники** — поставщики дополнительных демографических и гео-данных для профиля клиента.
  * **S3 / MinIO** — объектное хранилище бинарных артефактов (ML-моделей).
  * **Data Lake (S3 + Iceberg)** — хранилище сырых исторических транзакций для аналитики и дообучения.
* **Проектируемые командой сервисы:**
  * **Статистика клиента (Gateway / Features)** — точка входа, прием событий и обогащение агрегатами.
  * **ML-сервис** — вычислительный узел для инференса ML-моделей.
  * **Решение (Rules)** — узел бизнес-логики, формирующий итоговый вердикт (1/0).
  * **Загрузчик ETL** — фоновый процесс для агрегации данных и сохранения истории.
  * **Кэш (Redis 7)** — in-memory хранилище предрассчитанных признаков.

## 3. Перечень REST-взаимодействий и передаваемые данные

**Перечень REST-взаимодействий:**
1. **АБС -> Статистика клиента (Gateway):** АБС передает объект `TransactionRequest` (сумма, счета, время). Сервис возвращает `TransactionVerdictResponse` (вердикт одобрено/фрод).
2. **Статистика клиента -> ML-сервис (Inference API):** Интеграция также доступна по REST (помимо gRPC) для тестирования инференса. Передаются признаки клиента (`features`), возвращается скор вероятности фрода (от 0 до 1) и детали проверки.
3. **Мониторинг -> ML-сервис (Inference API):** Запрос списка загруженных в память моделей из S3.

## 5. Ограничения по времени ответа, объёму и свежести данных
* **Ограничения по времени (SLA):** Взаимодействие с АБС является синхронным. Жесткий SLA по времени ответа на запрос проверки транзакции составляет не более **100 мс**.
* **Ограничения по объему (Пропускная способность):** Система рассчитана на HighLoad профиль (десятки тысяч RPS). Обработка такого объема за 100 мс обеспечивается за счет неблокирующего (асинхронного) I/O, отсутствия долгих блокировок БД на чтение и горизонтального масштабирования stateless-контейнеров.
* **Свежесть данных:** Данные профиля подтягиваются из in-memory кэша Redis (время ответа 1–3 мс). Исторические агрегаты обновляются асинхронно через ETL, поэтому проверка опирается на наиболее свежую статистику, зафиксированную на момент предыдущей закрытой транзакции, не блокируя текущий HTTP-запрос.

## 6. Обоснование границ API и принятые допущения
* **Выбор протоколов взаимодействия:** REST API выбран исключительно для внешних границ (АБС, внешние источники), так как обеспечивает универсальную интеграцию, простоту тестирования и читаемость контрактов. Межсервисные вызовы по критическому пути (Gateway -> ML -> Rules) скрыты за границами API и используют gRPC, что является осознанным допущением для снижения накладных расходов на сериализацию.
* **Идемпотентность (GET vs POST):** Метод `GET` применяется строго для получения данных без изменения состояния системы (списки моделей). Метод `POST` используется для операций, требующих сложной валидации входящих данных или создания бизнес-сущностей (оценка транзакции, инференс), что позволяет безопасно передавать объемные JSON-объекты в Request Body.
* **Стандартизация ошибок:** Все внешние контракты возвращают ошибки в едином формате (`ErrorResponse`), чтобы потребитель (АБС) мог программно парсить код ответа и текст ошибки без дополнительной логики ветвления.

## 8. Описание REST-операций

### 8.1 Back API: Точка входа (Gateway) - Проверка транзакции
* **Назначение:** Оценка банковской транзакции на мошенничество.
* **Потребитель:** Автоматизированная банковская система (АБС).
* **Метод и путь:** `POST /v1/transactions/evaluate`
* **Параметры пути и запроса:** Отсутствуют.
* **Необходимые заголовки:**
  * `Content-Type: application/json` — указывает, что данные передаются в формате JSON.
* **Тело запроса (Request Body):** Обязательное, передается в формате JSON (схема `TransactionRequest`). Содержит поля:
  * `transaction_id` (string) — уникальный ID транзакции из АБС (пример: `tx-777`).
  * `account_id` (string) — идентификатор счета клиента (пример: `acc-12345`).
  * `amount` (number) — сумма транзакции (строго больше 0.0).
  * `currency` (string, по умолчанию `RUB`) — валюта операции.
  * `timestamp` (string) — время отправки транзакции (пример: `2026-09-21T10:00:00Z`).
* **Успешный статус и схема ответа:**
  * `200 OK` — Вердикт готов. Возвращает JSON `TransactionVerdictResponse` с полями `transaction_id`, `verdict` (где 0 - Одобрено, 1 - Фрод) и `evaluated_at`.
* **Применимые ошибки (схема `ErrorResponse` с полями `code` и `message`):** 
  * `400 Bad Request` — АБС прислала битые/нечитаемые данные (пример: `{"code": "BAD_REQUEST", "message": "Неверная сумма"}`).
  * `404 Not Found` — Эндпоинт не найден.
  * `422 Unprocessable Entity` — Ошибка бизнес-валидации (например, передана отрицательная сумма).
  * `500 Internal Server Error` — Внутренняя ошибка сервиса.

### 8.2 Front Service API: Внутренний сервис инференса

**А. Получение скора по признакам**
* **Назначение:** Принимает признаки клиента от сервиса статистики, применяет модель и возвращает скор. Решение выносит отдельный контейнер "Решение".
* **Метод и путь:** `POST /inference/check`
* **Параметры:** Отсутствуют.
* **Необходимые заголовки:**
  * `Content-Type: application/json` — указывает, что данные передаются в формате JSON.
* **Тело запроса (Request Body):** Обязательное, JSON (схема `InferenceRequest`). Содержит поля:
  * `transaction_id` (string) — ID транзакции.
  * `client_id` (string) — ID клиента.
  * `features` (object) — признаки клиента (строго требуются `avg_amount_30d` и `tx_count_24h`, опционально `geo_risk` и `merchant_risk`).
* **Успешный статус и схема ответа:**
  * `200 OK` — Скор от модели рассчитан. Возвращает объект `InferenceResponse` с полями `transaction_id`, `score` (число float от 0 до 1) и деталями `check_details` (`tool`, `version`, `action`, `actual_result`).
* **Применимые ошибки (схема `ErrorResponse` с полем `error`):** 
  * `400 Bad Request` — Нарушена структура признаков (пример: `{"error": "Invalid features data"}`).
  * `500 Internal Server Error` — Внутренняя ошибка при выполнении инференса (пример: `{"error": "ML model not loaded"}`).

**Б. Получение списка моделей для инференса**
* **Назначение:** Показывает, какие модели лежат в S3 и доступны для инференса.
* **Метод и путь:** `GET /models`
* **Тело запроса:** Отсутствует.
* **Успешный статус и схема ответа:**
  * `200 OK` — Список моделей успешно получен. Возвращает массив объектов `ModelInfo` с полями `name`, `version`, `status` (`active` или `archived`).
* **Применимые ошибки (схема `ErrorResponse` с полем `error`):** 
  * `500 Internal Server Error` — Не удалось получить список моделей (пример: `{"error": "Failed to fetch model list"}`).
