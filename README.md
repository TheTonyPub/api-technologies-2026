# Платформа данных по юридическим лицам

## 1. Взаимодействие сервисов

Платформа выступает единым источником данных о юридических лицах для
внутренних потребителей банка. Внешние источники и внутренние системы не
работают с хранилищами напрямую: загрузка, обработка, выдача данных и
интеграции разделены между специализированными сервисами.

### 1.1. Загрузка данных из СПАРК Интерфакс

1.  Процесс начинается с получения данных о юридическом лице из внешнего
    источника **СПАРК Интерфакс**.
2.  Компонент **Loader** обращается к СПАРК Интерфакс по протоколу
    **REST** и передаёт параметры, необходимые для поиска юридического
    лица.
3.  СПАРК Интерфакс возвращает данные о юридическом лице в ответе
    внешнего API.
4.  Loader принимает полученный ответ, выполняет необходимую первичную
    обработку и сохраняет данные во внутреннее историческое хранилище
    **Historical Store**.

Таким образом, внешний источник отделён от остальных компонентов
платформы: остальные сервисы работают с внутренними данными и не зависят
от необходимости самостоятельно обращаться к СПАРК.

### 1.2. Хранение истории в формате SCD2

Для Historical Store используется подход **SCD2 (Slowly Changing
Dimension Type 2)**. Его смысл заключается в том, что при изменении
данных старая версия записи не удаляется и не перезаписывается.

Для каждой версии данных сохраняется период её действия:

-   дата начала действия версии;
-   дата окончания действия версии;
-   сами значения атрибутов юридического лица;
-   при необходимости --- технические признаки актуальности версии.

Например, если у юридического лица изменился адрес, в Historical Store
остаётся предыдущая запись со старым адресом и периодом её действия, а
новая версия сохраняется отдельной записью с новым адресом. Благодаря
этому можно восстановить состояние данных на определённый момент времени
и проследить историю изменений.

Для реализации такого хранилища предполагается использовать
**PostgreSQL**.

### 1.3. Обогащение данных

После загрузки данные из Historical Store обрабатывает **Enrichment
Service**.

1.  Enrichment Service читает данные из Historical Store.
2.  Сервис выполняет необходимые операции обогащения и подготовки данных
    для оперативного использования.
3.  Результатом обработки становится актуальный срез информации о
    юридических лицах.
4.  Актуальный срез записывается в **Online Data Mart**.

Разделение Historical Store и Online Data Mart позволяет одновременно
решать две разные задачи: сохранять полную историю изменений и быстро
отдавать актуальное состояние данных потребителям.

### 1.4. Кэширование редко изменяющихся данных

Рядом с Online Data Mart используется **Cache**. В него помещаются
данные, которые меняются относительно редко и поэтому нет необходимости
каждый раз получать их из основного оперативного хранилища.

Для каждой категории кэшируемых данных задаётся **TTL (Time To Live)**
--- время жизни записи в кэше. После истечения TTL значение считается
устаревшим и должно быть заново получено из источника и помещено в кэш.

Для реализации Cache предполагается использовать **Redis**. Такой подход
позволяет снизить количество обращений к Online Data Mart и уменьшить
задержку при повторных запросах одних и тех же данных.

### 1.5. Единая точка входа для внутренних систем

Потребителями платформы являются, в частности, **CRM** и **АБС**. Они не
обращаются напрямую к Online Data Mart, Cache или отдельным внутренним
сервисам.

Запрос от CRM или АБС проходит через единый **API Gateway**:

1.  CRM или АБС формирует запрос по **REST**.
2.  Данные запроса передаются в формате **JSON**.
3.  API Gateway принимает запрос и определяет, какой внутренний сервис
    должен его обработать.
4.  Gateway проксирует запрос в соответствующий сервис.
5.  Сервис получает необходимые данные из Online Data Mart и/или Cache.
6.  Результат возвращается через Gateway потребителю в формате JSON.

Такой подход скрывает внутреннюю структуру платформы от потребителей.
Для CRM и АБС существует единая точка входа, а изменение внутренней
декомпозиции сервисов не требует менять интеграционный контракт каждого
потребителя.

### 1.6. Получение информации о клиенте

Для запроса информации по конкретному юридическому лицу Gateway
направляет запрос в **Client Info Service**.

Client Info Service использует **ИНН** как ключ поиска клиента, получает
актуальные данные из Online Data Mart или Cache и возвращает их
потребителю.

Последовательность выглядит следующим образом:

**CRM / АБС → API Gateway → Client Info Service → Online Data Mart /
Cache → API Gateway → CRM / АБС.**

Таким образом, потребителю не требуется знать, где именно физически
хранятся данные.

### 1.7. Получение компаний группы

Для получения всех клиентов, относящихся к одной группе компаний,
Gateway направляет запрос в **Group Companies Service**.

Сервис определяет состав группы на основании данных платформы, читает
необходимые сведения из Online Data Mart и Cache и формирует ответ со
связанными юридическими лицами.

Последовательность взаимодействия:

**CRM / АБС → API Gateway → Group Companies Service → Online Data Mart /
Cache → API Gateway → CRM / АБС.**

Выделение этой функции в отдельный сервис позволяет не смешивать поиск
одного клиента с логикой определения состава группы компаний.

### 1.8. Расчёт вероятности привлечения юридического лица

Для сценария скоринга используется **Scoring Service**.

1.  CRM или АБС отправляет запрос через API Gateway.
2.  Gateway передаёт запрос в Scoring Service.
3.  Scoring Service получает необходимые признаки юридического лица из
    Online Data Mart и/или Cache.
4.  Для расчёта сервис обращается к отдельной **ML-модели**.
5.  ML-модель возвращает рассчитанное значение вероятности того, что
    юридическое лицо станет клиентом.
6.  Scoring Service формирует ответ и возвращает его через API Gateway
    исходному потребителю.

При этом ML-модель является отдельным компонентом и не смешивается с
API-контрактом внешних потребителей. Для взаимодействия с моделью может
использоваться **gRPC**, если это соответствует требованиям к
производительности и контракту сервиса модели.

Итоговая цепочка имеет вид:

**CRM / АБС → API Gateway → Scoring Service → Online Data Mart / Cache →
ML-модель → Scoring Service → API Gateway → CRM / АБС.**

### 1.9. Передача данных в аналитический контур

Помимо оперативной выдачи данных внутренним системам, платформа передаёт
данные в **Аналитический контур банка**.

Это отдельное направление использования данных: аналитический контур
получает подготовленные сведения для последующего анализа и построения
аналитических решений. При этом аналитические потребители не должны
влиять на оперативные API-сценарии CRM и АБС.

Таким образом, общий поток данных можно представить в следующем виде:

**СПАРК Интерфакс → Loader → Historical Store (SCD2) → Enrichment
Service → Online Data Mart → API Gateway → внутренние сервисы → CRM /
АБС**

При этом:

-   **Cache** используется сервисами выдачи для часто запрашиваемых и
    редко изменяющихся данных;
-   **Scoring Service** дополнительно взаимодействует с ML-моделью;
-   подготовленные данные отдельно передаются в **Аналитический
    контур**.

## 2. Обоснование выбора технологий

Выбранные технологии соответствуют различным типам нагрузки и
ответственности компонентов. Внешние интеграции построены на REST/JSON,
историческое хранилище использует реляционную модель с поддержкой SCD2,
оперативная выдача ускоряется Redis-кэшем, а взаимодействие со
специализированной ML-моделью при необходимости может быть выполнено
через gRPC.

### 2.1. PostgreSQL для Historical Store

**PostgreSQL** предлагается использовать в качестве Historical Store,
потому что данные о юридических лицах имеют выраженную структурированную
и реляционную природу.

Для SCD2 особенно важны следующие свойства:

-   транзакционность операций;
-   ограничения целостности;
-   индексы по ИНН и датам действия версий;
-   возможность выполнять сложные SQL-запросы;
-   надёжное хранение большого количества исторических версий;
-   поддержка резервного копирования и восстановления;
-   возможность явно контролировать границы периодов действия записей.

SCD2 удобно реализуется как набор версий одной бизнес-сущности.
Например, для одного ИНН может существовать несколько исторических
строк, каждая из которых соответствует определённому периоду действия
данных.

PostgreSQL в данном случае выполняет роль источника исторической правды,
а не только временного буфера. Это позволяет не терять предыдущие
значения и при необходимости восстанавливать состояние данных на прошлые
даты.

### 2.2. Redis для Cache

**Redis** используется для кэширования редко изменяющихся данных и
снижения нагрузки на Online Data Mart.

Основные причины выбора:

-   высокая скорость операций чтения;
-   работа с данными в памяти;
-   поддержка TTL;
-   простая модель key-value для типовых кэшируемых объектов;
-   возможность контролировать время актуальности каждой записи.

TTL особенно важен для данной архитектуры: кэш не должен становиться
самостоятельным бессрочным источником истины. После истечения заданного
времени данные должны быть обновлены из основного источника.

В результате Redis используется как ускоряющий слой, а не как замена
постоянному хранилищу.

### 2.3. REST/JSON для внешних интеграций

Для взаимодействия с CRM и АБС выбран **REST API с JSON**.

Это соответствует характеру интеграции: CRM и АБС являются внешними по
отношению к платформе потребителями, которым нужен понятный и стабильный
контракт.

REST/JSON позволяет:

-   стандартизировать API;
-   явно описывать HTTP-методы и ресурсы;
-   передавать структурированные данные;
-   упростить интеграцию разных технологических стеков;
-   использовать единый API Gateway;
-   независимо развивать внутренние сервисы за пределами внешнего
    контракта.

Использование Gateway дополнительно позволяет централизовать такие
технические вопросы, как маршрутизация запросов, аутентификация и
авторизация, логирование, контроль доступа и единообразная обработка
ошибок.

### 2.4. gRPC для взаимодействия со Scoring и ML-моделью

Для связи **Scoring Service** с отдельной ML-моделью может
использоваться **gRPC**.

Такой вариант логичен именно для внутреннего взаимодействия, где обе
стороны находятся под контролем команды платформы и можно заранее
определить строгий контракт.

Преимущества gRPC в этом сценарии:

-   компактный бинарный формат сообщений;
-   строгая типизация контракта;
-   генерация клиентского и серверного кода;
-   удобное взаимодействие между сервисами;
-   низкие накладные расходы для частых внутренних вызовов.

При этом использование gRPC не обязательно распространять на CRM и АБС:
для внешнего API сохраняется REST/JSON, а внутреннее взаимодействие с
ML-моделью можно оптимизировать отдельно.

  Получение данных ЮЛ                 CRM / АБС → API Gateway → Client

Таким образом, архитектура покрывает полный жизненный цикл данных: от

потребителям, расчёта скоринга и передачи данных в аналитический контур.
