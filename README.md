## Описание кейса

Система забирает данные о юридических лицах из внешнего источника СПАРК Интерфакс, сохраняет их в историческое хранилище с полным версионированием изменений (SCD2), обогащает внутренними данными банка и формирует актуальный срез в отдельной витрине. На основе этих данных система предоставляет сервисы получения информации о клиенте по ИНН, получения всех клиентов группы компаний и скоринга потенциального клиента с использованием ML-модели. Доступ к данным получают CRM, АБС и аналитический контур банка.

## Взаимодействие сервисов

Данные в систему попадают через **Loader**, который обращается к внешнему API СПАРК Интерфакс по протоколу HTTPS/REST и получает актуальную информацию по юридическому лицу.

Loader записывает полученные данные в **Historical Store** в формате SCD2. Это означает, что каждое изменение атрибута клиента сохраняется не поверх старой записи, а как новая версия с датами начала и окончания действия. Благодаря этому в хранилище всегда доступна полная история изменений по клиенту, а не только его текущее состояние.

**Enrichment Service** читает данные из Historical Store, дополняет их внутренними данными банка и записывает актуальный срез в **Online Data Mart** - облегчённую витрину, оптимизированную под быстрое чтение, а не под хранение истории.

Рядом с витриной находится **Cache**, который хранит редко изменяющиеся данные с заданным временем жизни (TTL), чтобы снизить нагрузку на витрину при повторяющихся запросах.

Внешние потребители - **CRM** и **АБС** - обращаются к системе не напрямую к отдельным сервисам, а через единый **API Gateway** по REST/JSON. Это единая точка входа, которая упрощает интеграцию для внешних систем.

API Gateway проксирует запрос в один из трёх сервисов в зависимости от того, что нужно потребителю:
- **Client Info Service** возвращает актуальную информацию о клиенте по ИНН, читая данные из Online Data Mart и Cache;
- **Group Companies Service** возвращает всех клиентов из группы компаний, также читая из Online Data Mart;
- **Scoring Service** считает вероятность того, что юридическое лицо станет клиентом банка. Для этого сервис читает данные клиента из Online Data Mart и дополнительно обращается к отдельной **ML Model**, которая возвращает вероятность.

Отдельно от сервисного слоя исторические и актуальные данные передаются в **Аналитический контур** банка для дальнейшего BI-анализа - это закрывает функциональное требование о доступности данных для аналитического контура.

## Обоснование выбора технологий

**REST и JSON** выбраны как протокол взаимодействия с внешними потребителями (CRM, АБС) через API Gateway. Это стандартный, широко поддерживаемый подход с низким порогом входа для интеграции, что напрямую отвечает нефункциональному требованию о максимальной простоте использования сервиса внешними потребителями.

**PostgreSQL** выбран для Historical Store, потому что для формата SCD2 критична надёжная работа с транзакциями и версиями записей - реляционная база с ACID-гарантиями обеспечивает целостность истории изменений лучше, чем большинство NoSQL-решений.

Для **Online Data Mart** рассматриваются PostgreSQL или ClickHouse - ключевой критерий здесь скорость чтения, так как нефункциональное требование задаёт время ответа системы не более 1 секунды. Витрина не хранит историю, только актуальный срез, что снижает объём данных и ускоряет выборки по сравнению с обращением напрямую к историческому хранилищу.

**Redis** выбран для Cache, потому что функциональное требование прямо указывает: редко изменяющиеся данные должны кэшироваться с заданным временем жизни. Redis поддерживает TTL из коробки, что напрямую закрывает это требование.

Между Client Info Service, Group Companies Service и Scoring Service данные читаются из Online Data Mart и Cache, а не из Historical Store - это ключевое архитектурное решение для соблюдения требования об ответе системы за 1 секунду, так как обращение к историческому хранилищу со всеми версиями записей потребовало бы больше времени.

Для соблюдения требования о цикле загрузки одного клиента за 10 секунд предполагается, что Loader обрабатывает клиентов независимо и может масштабироваться горизонтально; при необходимости между Loader и Historical Store может быть добавлена очередь (например, Kafka) для асинхронной и более равномерной обработки нагрузки.

## Соответствие требованиям задания

| Требование | Как реализовано |
|---|---|
| Функц. 1: данные доступны для CRM, АБС, аналитического контура | API Gateway отдаёт данные CRM и АБС; данные передаются в Аналитический контур напрямую из хранилища |
| Функц. 2: загрузка из СПАРК Интерфакс, хранение SCD2 | Loader получает данные по REST и пишет их в Historical Store (PostgreSQL, формат SCD2) |
| Функц. 3: обогащение из внутреннего исторического хранилища | Enrichment Service читает и обогащает данные из Historical Store |
| Функц. 4: актуальный срез в Online-витрину | Enrichment Service записывает результат в Online Data Mart |
| Функц. 5: сервис получения информации по ИНН | Client Info Service |
| Функц. 6: сервис получения всех клиентов группы компаний | Group Companies Service |
| Функц. 7: сервис скоринга потенциального клиента | Scoring Service + обращение к ML Model |
| Функц. 8: кэширование редко изменяющихся данных с TTL | Cache на Redis |
| НФТ 1: цикл загрузки 1 клиента - 10 сек | Независимая обработка клиентов в Loader, возможность горизонтального масштабирования и/или асинхронная очередь |
| НФТ 2: время ответа системы - 1 сек | Сервисы читают из Online Data Mart и Cache, а не из Historical Store напрямую |
| НФТ 3: максимальная простота использования внешними потребителями | Единая точка входа API Gateway, протокол REST/JSON |
