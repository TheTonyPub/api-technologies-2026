## Семинар 1. Проектирование взаимодействия сервисов

На семинаре команда получает один из семестровых кейсов и начинает проектировать его архитектуру:

1. Выделяет внешних потребителей и границы системы.
2. Определяет сервисы, их ответственность и основные данные.
3. Фиксирует взаимодействия между внешними потребителями, сервисами и хранилищами.
4. Начинает контекстную и контейнерную диаграммы C4.
5. Обсуждает возможные протоколы, базы данных и ограничения выбранного варианта.

В разных кейсах могут понадобиться разные протоколы и схемы взаимодействия. Выбор должен следовать требованиям конкретного варианта, а не единому шаблону для всех команд.

Исходники Mermaid и PNG-артефакты обязательны и должны описывать одну архитектуру. Если команда рисует схему в draw.io, можно дополнительно сохранить исходный `.drawio`, но после этого всё равно нужно воспроизвести диаграммы кодом Mermaid в нотации C4.

### Git LFS для графических артефактов

PNG и другие крупные бинарные форматы отслеживаются через Git LFS по правилам из `.gitattributes`. Перед добавлением диаграмм установите и активируйте Git LFS:

```sh
git lfs install
git add .gitattributes architecture/*.png
git lfs ls-files
```

В выводе `git lfs ls-files` должны присутствовать все PNG-диаграммы. Файлы `.mmd` остаются обычными текстовыми файлами Git.

## Командная работа

Домашнее задание и дальнейший проект коллективные. Каждый участник команды должен сделать хотя бы один содержательный commit в ветку ДЗ. Ориентир — не менее 2–3 осмысленных коммитов, но для команды большего состава их должно быть достаточно, чтобы вклад каждого участника был виден. Не объединяйте всю работу в один итоговый commit: история должна показывать, как команда последовательно уточняла архитектуру, диаграммы и документацию.

Порядок создания fork, рабочей ветки и pull request приведён в [основном README](https://github.com/TheTonyPub/api-technologies-2026/blob/main/README.md#как-сдавать-домашние-задания).

## Обоснование выбора технологий

### 1. Языки программирования 

* **Python:**
   * **Роль в проекте:** Используется для работы Ml-модели ('Ml-сервис'), получения дополнительных данных о клиенте ('Enrichment') и организации процессов регулярной загрузки данных ('ETL')
   * **Почему выбрали:** Python имеет все необходимые библиотеки для работы с искусственным  интеллектом и анализом данных 
* **Go:** 
   * **Роль в проекте:** Используется в сервисах, критичных к времени отклика ('Gateway' - точка входа, 'Features' - сбор агрегатов, 'Rules' - принятие решения ). Это важно для выполнения нефункционального требования по общей задержке 100 мс.
   * **Почему выбрали:** Язык обеспечивает высокую скорость обработки запросов и эффективное использование ресурсов сервера при высокой нагрузке 

---

### 2. Протоколы взаимодействия 

* **gRPC:**
   * Быстрая бинарная сериализация данных, строгая типизация через '.proto' - файлы. Расходы на передачу данных в разы ниже, чем у REST\JSON 
   * Основной протокол для межсервисного взаимодействия внутри антифрод-системы ('Gateway', 'Enrichment', 'Features', 'ml', 'Rules'). Позволяет сэкономить ценные миллисекунды

* **REST API:**
   * Обеспечивает гибкость интеграции банковской системой (АБС) с минимальной задержкой 

---

### 3. Базы данных и хранилица 

* **Redis 7:**
   * Данные хранятся прямо в оперативной памяти, что обеспечивает мгновенный доступ (1-3 миллисекунды)
   * Используется как быстрая витрина данных. В Redis заранее загружена готовая статистика по клиенту, которую система мгновенно подтягивает во время проверки 

* **ClickHouse 24:**
   * Высокая скорость чтения и агрегации больших объемов исторических данных, эффективное сжатие данных
   * Хранение полной истории транзакций клиентов. Используется для формирования аналитической витрины, пересчета агрегаторов и обучения новых ML-моделей 
* **S3 / MinIO:**
   * Удобное и надежное хранение бинарных артефактов любого размера 
   * Хранение версий обученных ML-моделей, выгружаемых аналитиками и подгружаемых ML-сервисом 

---

### 4. Ассинхронная обработка и фоновые процессы 

* **Kafka:**
   * Высокая пропускная способность, возможность асинхронной обработки событие без блокировки основного потока транзакции
   * Отвечает за сохранение истории транзакций 

* **Airflow:**
   * Удобный инструмент для мониторинга, автоматизации пакетов обработки данных
   * Регулярная загрузка исторических данных из АБС, расчет агрегатов и обновление данных в 'Redis' и 'ClickHouse'
