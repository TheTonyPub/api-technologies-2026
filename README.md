Продолжите проект своей команды. В ДЗ 1 вы спроектировали архитектуру, в ДЗ 2 описали REST-контракты, теперь реализуйте сервисы этой архитектуры:

## Что выдаётся команде

### Внешние сервисы (моки)

Все моки работают на одном домене за HTTPS. Данные в них сгенерированы и вымышлены, но одинаковы для всех команд и не меняются от перезапуска. Поэтому результат работы вашей системы можно проверить заранее (см. «Сценарий проверки»).

| Сервис | Путь | Протокол | Документация | Кейс |
|---|---|---|---|---|
| АБС банка | `/abs` | REST/JSON | [`/abs/docs`](https://api.external-services.dataprosvet.ru/abs/docs) | Антифрод, СПАРК |
| Бюро данных о клиентах «ДатаПрофиль» | `/client-data` | REST/JSON | [`/client-data/docs`](https://api.external-services.dataprosvet.ru/client-data/docs) | Антифрод |
| СПАРК | `/spark` | SOAP 1.1 | [`/spark/`](https://api.external-services.dataprosvet.ru/spark/), [WSDL](https://api.external-services.dataprosvet.ru/spark/ws?wsdl) | СПАРК |
| Мониторинг серверов ИС | `/monitoring` | REST/JSON | [`/monitoring/docs`](https://api.external-services.dataprosvet.ru/monitoring/docs) | Прогноз мощности |
| Уведомления (SendGrid + FCM) | `/notify` | REST/JSON | [`/notify/docs`](https://api.external-services.dataprosvet.ru/notify/docs) | Прогноз мощности |

Подробное описание моков с особенностями для каждого кейса и исходный код лежат в ветке [`infra/external-services`](https://github.com/TheTonyPub/api-technologies-2026/tree/infra/external-services/external-services). Правила генерации данных открыты, их можно читать.

Общие правила моков:

- **Ключ команды** передаётся в заголовке `X-API-Key`. В `/notify` он передаётся как `Authorization: Bearer <ключ>`, так же как в SendGrid и FCM. В `/spark` вместо ключа используется логин и пароль для операции `Authenticate`.
- **Ошибки** приходят в формате `{"code", "message", "traceId"}`, в ответе всегда есть `X-Request-Id`. `/notify` возвращает ошибки в форматах SendGrid и Google API, `/spark` — SOAP Fault.
- **Лимиты** считаются на ключ: 20 запросов/с, в `/monitoring` — 50, в `/spark` — 5 на команду. При превышении приходит 429 с заголовком `Retry-After`.
- **Сбои по запросу** включаются заголовком `X-Mock-Scenario`: `slow` (3 с), `timeout` (30 с, затем 504), `error` (500), `unavailable` (503), `ratelimit` (429). Этим заголовком проверяется устойчивость вашей системы.

### Ключи

Ключ команды и, для кейса СПАРК, логин и пароль выдаёт преподаватель. Храните их только в `.env`. В репозитории должен лежать только `.env.example` без значений. Ключ в истории коммитов — ошибка, после неё ключ придётся перевыпустить.

### Модели `.dill`

Каждой команде выдаётся одна готовая модель. Файл — это словарь из обычных объектов scikit-learn и метаданных `meta`: признаки с описанием (`meta["feature_doc"]`), порог, метрики и версии библиотек. Своего кода внутри файла нет.

| Файл | Кейс | Что внутри | Как вызвать |
|---|---|---|---|
| `antifraud-v1.dill` | Антифрод | `model` (HistGradientBoostingClassifier), `meta.threshold` | `model.predict_proba(df)[:, 1]`, вердикт 1, если `>= threshold` |
| `company-scoring-v1.dill` | СПАРК | `model` (Pipeline: OneHot + LogisticRegression) | `model.predict_proba(df)[:, 1]` |
| `capacity-forecast-v1.dill` | Прогноз мощности | `models[горизонт][mean\|peak]` (Ridge), горизонты `1d`, `1m`, `6m`, `1y` | `models["1m"]["peak"].predict(df)[0]` |

```python
import dill, pandas as pd

art = dill.load(open("antifraud-v1.dill", "rb"))
meta = art["meta"]
row = {"amount": 45000, "avg_amount_30d": 1800, "tx_count_24h": 3,
       "geo_risk": 0.75, "merchant_risk": 0.8, "hour": 22}
score = art["model"].predict_proba(pd.DataFrame([row], columns=meta["features"]))[0, 1]
verdict = int(score >= meta["threshold"])
```

Для загрузки нужны Python 3.11+, `scikit-learn==1.8.0`, `dill` и `pandas`. Признаки считайте строго по `meta["feature_doc"]`, иначе модель будет ошибаться. Не добавляйте `.dill` в git: сервис должен забирать модель при сборке или старте.

### Kafka локально

Если в вашей архитектуре есть Kafka, достаточно одного брокера `apache/kafka:4.1.0` в режиме KRaft, без ZooKeeper. Ограничьте ему память: `KAFKA_HEAP_OPTS="-Xms256m -Xmx256m"` и `mem_limit: 768m`. Так брокер занимает около 400 МБ и с большим запасом справляется с нагрузкой учебных кейсов.

## Обязательные критерии

Если не выполнен хотя бы один из первых трёх критериев, работа возвращается на доработку без оценки.

1. **Система поднимается локально одной командой** `docker compose up --build` на чистой машине. Поднимаются все сервисы, базы и брокеры команды, миграции и первичная загрузка проходят без ручных шагов. Ключи берутся из `.env`.
2. **Система корректно ходит во внешние API своего кейса.** Нужные заголовки и ключ, правильные пути, правильный формат REST или SOAP.
3. **Обрабатываются все данные.** Пройдены все страницы, загружены все сущности и вся история, нужная кейсу. В README укажите, сколько записей загружено. Это число должно сходиться с моками.
4. **Каждый участник пишет код.** У каждого есть свой сервис или компонент из списка кейса. В README должна быть таблица «участник → компонент», в истории должны быть осмысленные коммиты каждого в код. Документация и сборка PR не считаются участием в разработке. Участник без своего кода получает не больше 60% баллов команды, на баллы остальных это не влияет.

## Сценарий проверки

Данные моков детерминированы, поэтому ожидаемый результат каждого шага известен заранее. Эталон считает скрипт [`tools/expected.py`](https://github.com/TheTonyPub/api-technologies-2026/blob/infra/external-services/external-services/tools/expected.py) теми же формулами, что и моки, и теми же моделями. ### Что подготовить

Положите в репозиторий `scripts/demo.sh` — единую точку входа сценария. Скрипт должен:

- пройти шаги своего кейса из таблицы ниже только через публичные API своих сервисов;
- печатать каждый вызов и ответ;
- сохранить итоговые числа в `demo-result.json`.

Все исходящие вызовы во внешние моки должны добавлять заголовок `X-Mock-Scenario`, если задана переменная окружения `MOCK_SCENARIO`.

### Как проходит проверка

1. **Чистый старт.** `git clone` ветки PR, `cp .env.example .env` с ключом команды, `docker compose down -v && docker compose up -d --build`. Все контейнеры в состоянии healthy, первичная загрузка закончилась без ручных шагов.
2. **Сценарий.** Запускается `./scripts/demo.sh`, результат сверяется с эталоном на ту же дату и окно.
3. **Сбои.** Тот же шаг выполняется с `MOCK_SCENARIO=unavailable`, затем `ratelimit` и `timeout`. Сервис не падает, повторяет запрос и отвечает ошибкой по контракту.
4. **Идемпотентность.** Повторный запуск загрузки не меняет число записей. После `docker compose restart` данные на месте.
5. **Участники.** Каждый показывает свой шаг сценария в коде и отвечает на вопросы по своему компоненту.

## Как сдавать

1. Создайте в своём fork ветку `homework/04-api-services` от ветки последнего сданного ДЗ. Все материалы предыдущих работ должны сохраниться.
2. Если архитектура изменилась (gRPC вместо REST, сервис синхронизации вместо ETL и т. п.), обновите Mermaid-диаграммы, PNG и README.
3. Откройте pull request из `homework/04-api-services` своего fork в ветку `homework/04-api-services` основного репозитория.
4. В PR должны быть:
   - код сервисов, `docker-compose.yml`, `.proto`;
   - обновлённые OpenAPI-контракты;
   - `.env.example` без ключей;
   - `scripts/demo.sh`;
   - README с командой запуска, списком портов, числом загруженных записей и таблицей «участник → компонент».
5. В описании PR укажите состав команды, кто какой компонент делал и итоговый commit.

Каждый участник делает осмысленные коммиты в код своего компонента. Не объединяйте всю работу в один итоговый commit.
