### 2. Опишите границы REST API

В `api-design.md` зафиксируйте:

- состав команды, назначенный кейс и ссылку на архитектуру ДЗ 1;
- внешних потребителей, внешние системы и проектируемые командой сервисы;
- полный перечень REST-взаимодействий между внутренними сервисами и с внешними сервисами;
- кто, что и кому передаёт при каждом REST-взаимодействии;
- ссылку на OpenAPI-контракт каждого REST API;
- ограничения по времени ответа, объёму и свежести данных;
- обоснование границ API и принятые допущения;
- изменения архитектуры относительно ДЗ 1, если они понадобились.

Если два компонента взаимодействуют по gRPC, контракт этого взаимодействия в рамках ДЗ 2 можно описать словами: что предается, какую ручку дергаем, какие данные получаем обратно. Не подменяйте gRPC-контракт форматом OpenAPI.

### 3. Опишите каждый REST API

Для каждой операции каждого REST API опишите:

- назначение, потребителя, метод и путь;
- path- и query-параметры, необходимые заголовки и тело запроса;
- обязательные поля, типы, форматы, ограничения и допустимые значения;
- успешный статус и схему ответа;
- применимые ошибки и единый формат их представления;
- синтетические примеры корректного запроса, успешного ответа и хотя бы одной ошибки.

Методы и пути должны выражать смысл операции. Чтение не должно незаметно менять бизнес-состояние. Для длительной операции отдельно продумайте запуск, получение статуса и получение результата. Не добавляйте CRUD, пагинацию или асинхронную задачу без потребности конкретного кейса.

Если проект обращается к REST API внешнего сервиса, добавьте контракт используемой части этого API и явно отметьте в `api-design.md`, что сервис внешний. Если контракт основан на документации поставщика, приведите ссылку на источник и не выдавайте учебное описание за официальный контракт внешней системы.

### 4. Сохраните особенности кейса

- **Антифрод.** Покройте приём транзакции и возврат решения `1` или `0`. Объясните, что входит в общий цикл с ограничением 100 мс, какие данные готовятся заранее и что получает клиент, если решение принять невозможно.
- **СПАРК.** Покройте получение актуальных сведений по ИНН, состава группы компаний и результата скоринга. Различайте актуальный срез и историческое хранение SCD2, учитывайте время жизни кэша, цикл загрузки одного клиента до 10 секунд и ответ сервиса до 1 секунды. Не выдавайте учебные пути за реальные API СПАРК.
- **Прогноз серверных ресурсов.** Покройте доступ к текущим показателям, истории и прогнозам выбранной ИС. Сохраните сбор данных каждую минуту, горизонты в один день, месяц, шесть месяцев и год, NRT-данные для суточного прогноза и ответ до 1 секунды. Объясните свежесть данных и поведение при отсутствии готового результата.

Ограничение времени ответа остаётся проектным требованием и не считается доказанным без реализации и измерений.

## Разбалловка и защита ДЗ

Всего за семестр можно получить 100 баллов. Допуск на зачет начинается с 30 баллов за семестр.
|Баллы|Оценка|
|---:|---:|
|85 - 100|5|
|70 - 84|4|
|60 - 69|3|
|0 - 59|не сдали|

>[!note]
>Оставшиеся баллы для зачета можно будет набрать на финальной защите проекта или за индивидуальные задания.

За каждое ДЗ можно будет получить от 0 до 5 баллов. Будет 2 дедлайна -- soft и hard.

|Когда сдали|Максимальный балл|
|---|---|
|до soft|5|
|после soft до hard|3|
|после hard|0|

>[!CAUTION]
>Дедлайн и возможность получить максимальный балл распространяются на всю команду.
>При этом, если команда сдала работу до soft, но у кого-то конкретного нет ни одного коммита, либо коммит с каким-то небольшим нефункциональным изменением, то его максимальный возможный балл снижается до 3.

>[!important]
>ДЗ делается в группах, но сдается индивидуально.
>Во время самостоятельной практики на семинаре необходимо подойти к преподавателю и защитить выполненное ДЗ, ответив на вопросы преподавателя.
>Вопросы будут касаться теории из лекций, практического применения технологий с семинаров, а также самого ДЗ.
>
>P.S. gpt-код будет видно сразу, поэтому советую использовать gpt осознанно, потому что необходимо будет объяснять, что и как работает, почему выбран тот или иной метод, почему написана именно такая функция и т.д.

Один файл `openapi.yaml` описывает один API. Каждый контракт должен содержать все используемые операции API, параметры, схемы запросов и ответов, ограничения, успешные и ошибочные статусы, а также синтетические примеры. Используйте только вымышленные данные; не добавляйте пароли, токены, персональные данные и реальные адреса внутренних систем.

Проверьте каждый `openapi.yaml` валидатором и откройте его в совместимом средстве просмотра. Убедитесь, что ссылки разрешаются, операции и схемы отображаются, а примеры соответствуют схемам. В `api-design.md` запишите использованный инструмент и версию, выполненную команду или действия и фактический результат проверки. Запуск запросов к ещё не реализованному серверу не требуется.

Справочные материалы: [OpenAPI Specification 3.2.1](https://spec.openapis.org/oas/v3.2.1.html) и [Swagger Editor](https://editor.swagger.io/).

## Критерии самопроверки

- Покрыты основные сценарии выбранного кейса, а границы системы и фоновые действия объяснены.
- Все REST-взаимодействия между внутренними и внешними сервисами перечислены и описаны.
- Описание взаимодействий согласовано с C4-диаграммами ДЗ 1.
- По каждой операции понятно, кто её вызывает, что передаёт и что получает.
- HTTP-семантика, входные и выходные данные и ошибки описаны однозначно.
- Для каждого REST API есть отдельный проверенный контракт OpenAPI 3.2.1.
- Все файлы ДЗ 1, включая Mermaid-код и PNG-артефакты, сохранены и при необходимости обновлены.
- Допущения не выданы за реализованные или измеренные свойства системы.
- Серверный код отсутствует: на этом этапе сдаётся проектирование и документация.

## Командная работа

Распределите роли: например, документация, архитектурное проектирование, описание сервисов, выбор протоколов и разработка контрактов. Каждый участник команды должен сделать хотя бы один содержательный commit. Ориентир — не менее 2–3 осмысленных коммитов, но для команды большего состава их должно быть достаточно, чтобы вклад каждого участника был виден. Один commit со всей готовой работой не подходит.

Порядок создания fork, рабочей ветки и pull request приведён в [основном README](https://github.com/TheTonyPub/api-technologies-2026/blob/main/README.md#как-сдавать-домашние-задания).
