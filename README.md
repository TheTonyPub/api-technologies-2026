# API-технологии — 2026

## Семинар 2. От архитектуры к API-контрактам

На семинаре продолжите архитектуру из ДЗ 1 и перейдите от связей на C4-диаграммах к контрактам взаимодействия:

1. Выберите одну внешнюю и одну внутреннюю связь проекта.
2. Для каждой связи укажите инициатора, получателя, цель и передаваемые данные.
3. Определите протокол и модель взаимодействия: синхронную, асинхронную, событийную или потоковую.
4. Для HTTP-взаимодействия выделите ресурсы и разберите метод, путь, параметры, заголовки, тело, успешный ответ и ошибку.
5. Свяжите получившиеся операции с сервисами на C4-диаграмме.

В разных вариантах могут использоваться REST/HTTP, gRPC, WebSocket, события или другие подходящие схемы. Выбор протокола должен опираться на требования кейса, а не на единый шаблон для всех команд.

## Домашнее задание 2. Контракты взаимодействия

Продолжите проект из ДЗ 1: опишите протоколы внешних и внутренних взаимодействий, спроектируйте API между сервисами и подготовьте машиночитаемые контракты проектируемых HTTP API. Реализация серверов, обучение моделей и развёртывание в этом ДЗ не требуются.

Нормативная основа — практическая работа № 2 РПД: проектирование REST API и OpenAPI-спецификации. В РПД в качестве примера используются загрузка исходных данных, запуск расчёта, получение статуса обработки, получение результата и просмотр истории запросов. Перенесите эти типы операций в свой кейс только там, где они соответствуют его требованиям: создавать лишние эндпоинты ради формального совпадения не нужно.

### 1. Опишите границы и протоколы

В `api-design.md` зафиксируйте:

- состав команды, назначенный кейс и ссылку на архитектуру ДЗ 1;
- внешних потребителей, внешние системы и проектируемые командой сервисы;
- кто, что и кому передаёт при каждом существенном взаимодействии;
- отдельно выбранные протоколы для внешних и внутренних взаимодействий;
- синхронность или асинхронность обмена, ограничения по времени ответа, объёму и свежести данных;
- обоснование выбора протоколов и принятые допущения;
- изменения архитектуры относительно ДЗ 1, если они понадобились.

Если взаимодействие использует не HTTP, не описывайте его искусственно в OpenAPI. Зафиксируйте назначение, стороны, формат сообщений, успешный результат, ошибки и особенности выбранного протокола в `api-design.md`.

### 2. Спроектируйте HTTP API

Для каждой операции HTTP API опишите:

- назначение, потребителя, метод и путь;
- path- и query-параметры, необходимые заголовки и тело запроса;
- обязательные поля, типы, форматы, ограничения и допустимые значения;
- успешный статус и схему ответа;
- применимые ошибки и единый формат их представления;
- синтетические примеры корректного запроса, успешного ответа и хотя бы одной ошибки.

Методы и пути должны выражать смысл операции. Чтение не должно незаметно менять бизнес-состояние. Для длительной операции отдельно продумайте запуск, получение статуса и получение результата. Не добавляйте CRUD, пагинацию или асинхронную задачу без потребности конкретного кейса.

### 3. Сохраните особенности кейса

- **Антифрод.** Покройте приём транзакции и возврат решения `1` или `0`. Объясните, что входит в общий цикл с ограничением 100 мс, какие данные готовятся заранее и что получает клиент, если решение принять невозможно.
- **СПАРК.** Покройте получение актуальных сведений по ИНН, состава группы компаний и результата скоринга. Различайте актуальный срез и историческое хранение SCD2, учитывайте время жизни кэша, цикл загрузки одного клиента до 10 секунд и ответ сервиса до 1 секунды. Не выдавайте учебные пути за реальные API СПАРК.
- **Прогноз серверных ресурсов.** Покройте доступ к текущим показателям, истории и прогнозам выбранной ИС. Сохраните сбор данных каждую минуту, горизонты в один день, месяц, шесть месяцев и год, NRT-данные для суточного прогноза и ответ до 1 секунды. Объясните свежесть данных и поведение при отсутствии готового результата.

Ограничение времени ответа остаётся проектным требованием и не считается доказанным без реализации и измерений.

### 4. Подготовьте OpenAPI-контракты

Для каждого проектируемого сервиса с HTTP API создайте отдельный файл:

```text
contracts/
  <service-name>/
    openapi.yaml
```

Используйте OpenAPI 3.2.1. Каждый контракт должен содержать все проектируемые операции сервиса, параметры, схемы запросов и ответов, ограничения, успешные и ошибочные статусы, а также синтетические примеры. Используйте только вымышленные данные; не добавляйте пароли, токены, персональные данные и реальные адреса внутренних систем.

Проверьте каждый `openapi.yaml` валидатором и откройте его в совместимом средстве просмотра. Убедитесь, что ссылки разрешаются, операции и схемы отображаются, а примеры соответствуют схемам. В `api-design.md` запишите использованный инструмент и версию, выполненную команду или действия и фактический результат проверки. Запуск запросов к ещё не реализованному серверу не требуется.

Справочные материалы: [OpenAPI Specification 3.2.1](https://spec.openapis.org/oas/v3.2.1.html) и [Swagger Editor](https://editor.swagger.io/).

## Что должно быть в репозитории

```text
api-design.md
contracts/
  <service-name>/openapi.yaml
```

Если HTTP API проектируют несколько сервисов, добавьте отдельный каталог и `openapi.yaml` для каждого из них.

## Критерии самопроверки

- Покрыты основные сценарии выбранного кейса, а границы системы и фоновые действия объяснены.
- Внешние и внутренние протоколы названы и обоснованы.
- Описание взаимодействий согласовано с C4-диаграммами ДЗ 1.
- По каждой операции понятно, кто её вызывает, что передаёт и что получает.
- HTTP-семантика, входные и выходные данные и ошибки описаны однозначно.
- Для каждого проектируемого HTTP-сервиса есть отдельный проверенный `openapi.yaml`.
- Допущения не выданы за реализованные или измеренные свойства системы.
- Серверный код отсутствует: на этом этапе сдаётся проектирование и документация.

## Командная работа

Распределите роли: например, документация, архитектурное проектирование, описание сервисов, выбор протоколов и разработка контрактов. Каждый участник команды должен сделать хотя бы один содержательный commit. Ориентир — не менее 2–3 осмысленных коммитов, но для команды большего состава их должно быть достаточно, чтобы вклад каждого участника был виден. Один commit со всей готовой работой не подходит.

## Как сдавать

1. Один участник команды делает fork основного репозитория и добавляет остальных участников как collaborators в fork.
2. В fork команда переключается на ветку `seminar/02-openapi-contract`.
3. От неё создаётся ветка `homework/02-<short-name>`, где `<short-name>` — короткое название проекта или задания.
4. Все материалы ДЗ и их история коммитов создаются в ветке домашнего задания.
5. Команда открывает pull request из `homework/02-<short-name>` своего fork в ветку `seminar/02-openapi-contract` основного репозитория.
6. В описании PR укажите состав команды, кейс, распределение ролей, пути к `api-design.md` и контрактам, связь с ДЗ 1, результаты проверки и итоговый commit.

Для сдачи передаётся ссылка на pull request.
