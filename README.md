## Описание кейса

Проектируется информационная система прогнозирования потребления ресурсов серверов (CPU, RAM, диск), обслуживающих другие информационные системы (ИС) компании.

Функциональные требования:

1. Сбор метрик нагрузки на серверы ИС с периодичностью раз в минуту.
2. Загрузка собранных данных в долгосрочное хранилище.
3. Пользовательский интерфейс (UI) для доступа к системе.
4. Сервис применения модели прогнозирования нагрузки на серверы выбранной ИС на горизонтах 1 день, 1 месяц, 6 месяцев и 1 год.
5. Хранение информации о серверах и их принадлежности к ИС.
6. Уведомление пользователей о том, что прогнозируемая нагрузка на сервер в перспективе 1 дня или 1 месяца превысит допустимую.
7. Для прогноза на 1 день данные должны поступать в режиме, близком к реальному времени (NRT — near real time).
8. К системе подключён ситуационный центр со своим dashboard, отображающим актуальное и прогнозируемое состояние серверов.

## Архитектура

### Контекстная диаграмма (C4, уровень 1)

Исходный код: [`architecture/context-diagram.mmd`](architecture/context-diagram.mmd)
Экспорт: [`architecture/context-diagram.png`](architecture/context-diagram.png)

Систему окружают:

- **Инженер / DevOps-инженер** — настраивает серверы, ИС и допустимые пороги нагрузки, просматривает историю и прогнозы, получает уведомления.
- **Серверы информационных систем** (внешняя система) — источник метрик CPU/RAM/диска; передаёт их в систему каждую минуту через агентов мониторинга.
- **Ситуационный центр** (внешняя система) — запрашивает и получает от системы актуальное и прогнозируемое состояние серверов для отображения на собственном dashboard.
- **Каналы уведомлений (Email/Push)** (внешняя система) — доставляют пользователям уведомления о превышении допустимой нагрузки.

### Контейнерная диаграмма (C4, уровень 2)

Исходный код: [`architecture/containers-diagram.mmd`](architecture/containers-diagram.mmd)
Экспорт: [`architecture/containers-diagram.png`](architecture/containers-diagram.png)

Система разбита на четыре логические группы контейнеров:

- **Доступ** — `Web UI`, `API`. Единая точка входа для инженера (через Web UI) и для ситуационного центра (напрямую через API): аутентификация, чтение и настройка серверов/ИС/порогов, чтение прогнозов и текущего состояния.
- **Приём и потоковая обработка** — `Metrics Collector`, `Kafka`, `Stream Processor`. Metrics Collector принимает сырые метрики от серверов раз в минуту и публикует их в Kafka; Kafka буферизует поток и развязывает отправителей от обработчиков; Stream Processor (Apache Flink) читает поток из Kafka и в реальном времени считает NRT-агрегаты (фичи), которые кладёт в Hot Store, а также пишет историю в Data Store.
- **Прогнозирование и алерты** — `Forecast Worker`, `Alert Worker`. Forecast Worker строит прогнозы на всех горизонтах (1 день — по NRT-фичам из Hot Store, 1 мес/6 мес/1 год — по истории из Data Store); Alert Worker сравнивает прогнозы на 1 день и 1 месяц с допустимыми порогами и инициирует уведомления.
- **Хранилища** — `Hot Store` (Redis) для готовых NRT-фич, используемых при прогнозе на горизонте 1 день, и `Data Store` (TimescaleDB/PostgreSQL) — единое хранилище истории метрик, метаданных серверов/ИС/порогов и готовых прогнозов.

## Взаимодействие сервисов

Ниже описано, кто, что и кому передаёт при взаимодействии сервисов между собой и с внешними потребителями.

| Отправитель | Получатель | Что передаётся | Протокол |
|---|---|---|---|
| Инженер | Web UI | Просмотр истории и прогнозов, настройка серверов/ИС/порогов | HTTPS |
| Web UI | API | Запрос данных: серверы, ИС, прогнозы, пороги | HTTPS/JSON |
| Ситуационный центр | API | Запрос актуального и прогнозируемого состояния | HTTPS/WebSocket |
| Серверы ИС (агенты мониторинга) | Metrics Collector | Сырые метрики CPU/RAM/диска, каждую минуту | HTTP |
| Metrics Collector | Kafka | Публикация сырых метрик | Kafka protocol (produce) |
| Kafka | Stream Processor | Поток сырых метрик | Kafka protocol (consume) |
| Stream Processor | Hot Store | Запись предрасчитанных NRT-фич | Redis protocol |
| Stream Processor | Data Store | Запись истории метрик (агрегаты) | SQL |
| API | Data Store | Чтение/запись серверов, ИС, порогов; чтение прогнозов | SQL |
| Forecast Worker | Hot Store | Чтение NRT-фич (для прогноза на 1 день) | Redis protocol |
| Forecast Worker | Data Store | Чтение истории (для 1 мес / 6 мес / 1 год), сохранение прогнозов | SQL |
| Alert Worker | Data Store | Чтение прогнозов (1 день / 1 месяц) и допустимых порогов | SQL |
| Alert Worker | Каналы уведомлений (Email/Push) | Уведомление о превышении допустимой нагрузки | SMTP / HTTP webhook |

## Обоснование выбора технологий

### Протоколы

- **HTTP между агентами и Metrics Collector.** Каждый сервер раз в минуту отправляет компактный набор показателей — простой push-запрос, без постоянного соединения. Рассматривали и альтернативу — отдельный воркер, который собирал бы метрики прямо из логов серверов, не нагружая их дополнительным сетевым вызовом; сознательно выбрали явный push от агента, потому что он даёт единый протокол независимо от того, что и как логирует конкретная ИС, и гарантированный интервал ровно раз в минуту, не зависящий от формата и частоты ротации логов на каждом сервере.
- **Kafka (Kafka protocol) между Metrics Collector, Stream Processor и далее.** Изначально мы соединяли сборщик метрик напрямую с хранилищами по HTTP/SQL-вызовам, но при таком подходе сборщик становится узким местом и жёстко завязывает отправителей на доступность обработчика. Kafka решает это: развязывает продюсеров (Metrics Collector) и консьюмеров (Stream Processor), сглаживает всплески нагрузки (если метрик приходит больше обычного) и позволяет в будущем подключить ещё консьюмеров к тому же потоку без изменения Metrics Collector.
- **Redis (протокол Redis) для Hot Store.** Сама Redis используется только для быстрой записи/чтения уже готового результата, а не для обработки: агрегаты метрик за скользящее окно (например, за последние ~30 минут) считает отдельно Stream Processor на Flink, читая сырой поток из Kafka, и в Redis кладёт уже посчитанные NRT-фичи — поэтому прогноз на 1 день читает их с минимальной задержкой, не выполняя вычисления на лету.
- **REST/HTTPS + JSON на внешнем контуре** (Web UI ↔ API; Ситуационный центр ↔ API). Внешним клиентам важны простота интеграции, читаемость и широкая поддержка инструментов — REST/JSON остаётся стандартом де-факто для таких интеграций.
- **WebSocket в дополнение к REST для запросов ситуационного центра.** Ситуационный центр — это отдельное веб-приложение с dashboard, которое при открытии страницы устанавливает WebSocket-соединение с API. Дальше при каждом обновлении текущего состояния или прогноза (не реже раза в минуту, сразу после обработки новых метрик) API рассылает всем подключённым клиентам JSON-сообщение с изменившимися значениями (например, `{serverId, currentLoad, forecast1d}`), и dashboard на стороне ситуационного центра перерисовывает нужный виджет без перезагрузки страницы и без периодического опроса API.
- **SMTP/HTTP webhook для уведомлений.** Уведомления о превышении порогов на 1 день и 1 месяц не требуют мгновенной доставки и синхронного ответа. По сути webhook — это обычный исходящий REST-вызов к провайдеру уведомлений в момент срабатывания алерта, просто так называют приём асинхронных событий большинство внешних сервисов рассылки (SendGrid, Firebase и подобные); если бы у провайдера не было отдельного webhook-эндпоинта, ничего не мешало бы вызывать его обычный REST API тем же способом.
- **SQL для обращений к Data Store.** Все сервисы (API, Stream Processor, Forecast Worker, Alert Worker) читают и пишут данные в единую реляционную/time-series СУБД — прямые SQL-запросы проще в разработке и отладке, чем городить отдельный сервисный слой поверх хранилища на этом масштабе системы.

### Базы данных

- **Redis (Hot Store) для NRT-фич.** Прогноз на 1 день требует near real-time доступа к уже посчитанным признакам с минимальной задержкой чтения — Stream Processor заранее считает эти агрегаты из потока и кладёт готовый результат в in-memory хранилище, снимая эту нагрузку с основной БД.
- **TimescaleDB/PostgreSQL (Data Store) как единое хранилище.** Метрики поступают ежеминутно и должны храниться минимум на горизонте 1 год для долгосрочных прогнозов — расширение TimescaleDB поверх PostgreSQL даёт эффективное хранение и агрегацию временных рядов, при этом остаётся обычной реляционной СУБД для данных о серверах, ИС, пользователях, порогах и прогнозах со связями между ними (внешние ключи сервер → ИС, прогноз → сервер). Одна технология вместо нескольких разных СУБД снижает сложность эксплуатации, что оправдано для системы такого масштаба.

### Прочие существенные технологии

- **Apache Kafka как буфер потока метрик.** Добавлена по итогам обсуждения архитектуры: прямая передача метрик по HTTP от сборщика к обработчикам плохо масштабируется и жёстко связывает компоненты между собой. Kafka разрывает эту связь, накапливает поток сырых метрик и позволяет читать его с той скоростью, с которой готов обрабатывать Stream Processor, не теряя данные при кратковременных нагрузках.
- **Apache Flink как Stream Processor.** Необходим отдельный модуль, который превращает сырые метрики в готовые для модели признаки (фичи) — считает агрегаты (например, средние/максимумы за окно времени) над потоком из Kafka в реальном времени. Flink выбран, потому что это специализированный фреймворк потоковой обработки с нативной интеграцией с Kafka как источником и умеет писать результат в Redis — то есть закрывает весь путь от сырого потока до готовых NRT-фич без промежуточных самописных сервисов.
- **Go для Metrics Collector и Alert Worker.** Оба сервиса выполняют много параллельных операций ввода-вывода (Collector — приём метрик от множества серверов одновременно, Alert Worker — параллельные проверки порогов и отправка уведомлений): лёгкие горутины и встроенная модель конкурентности в Go дают высокую пропускную способность при низких накладных расходах, что подходит для таких stateless-сервисов, масштабируемых горизонтально.
- **Единый API-сервис** вместо отдельного шлюза и набора микросервисов — на масштабе этой системы (один UI, один внешний потребитель — ситуационный центр) достаточно одного сервиса, отвечающего за аутентификацию и доступ к данным, без избыточного дробления на множество сервисов.
