# API-технологии — 2026

## Семинар 1. Проектирование взаимодействия сервисов

На семинаре команда получает один из семестровых кейсов и начинает проектировать его архитектуру:

1. Выделяет внешних потребителей и границы системы.
2. Определяет сервисы, их ответственность и основные данные.
3. Фиксирует взаимодействия между внешними потребителями, сервисами и хранилищами.
4. Начинает контекстную и контейнерную диаграммы C4.
5. Обсуждает возможные протоколы, базы данных и ограничения выбранного варианта.

В разных кейсах могут понадобиться разные протоколы и схемы взаимодействия. Выбор должен следовать требованиям конкретного варианта, а не единому шаблону для всех команд.

## Домашнее задание 1. Архитектура командного проекта

Завершите архитектуру назначенного команде кейса. Код сервисов в этом ДЗ писать не нужно.

### Что должно быть в репозитории

1. Контекстная диаграмма C4, уровень 1: система, внешние потребители и внешние системы.
2. Контейнерная диаграмма C4, уровень 2: проектируемые сервисы, хранилища и связи между ними.
3. `README.md` с описанием того, кто, что и кому передаёт при взаимодействии сервисов между собой и с внешними потребителями.
4. В `README.md` — обоснование выбора протоколов, баз данных и других существенных технологий.
5. Состав команды, назначенный кейс и распределение ролей: например, документация, архитектурное проектирование, описание сервисов, выбор протоколов и подготовка диаграмм.

Диаграммы должны храниться в репозитории или открываться по доступной всем проверяющим ссылке. Описания должны соответствовать диаграммам и не противоречить друг другу.

## Командная работа

Домашнее задание и дальнейший проект коллективные. Каждый участник команды должен сделать хотя бы один содержательный commit в ветку ДЗ. Ориентир — не менее 2–3 осмысленных коммитов, но для команды большего состава их должно быть достаточно, чтобы вклад каждого участника был виден. Не объединяйте всю работу в один итоговый commit: история должна показывать, как команда последовательно уточняла архитектуру, диаграммы и документацию.

## Как сдавать

1. Один участник команды делает fork основного репозитория и добавляет остальных участников как collaborators в fork.
2. В fork команда переключается на ветку `seminar/01-api-scenarios`.
3. От неё создаётся ветка `homework/01-<short-name>`, где `<short-name>` — короткое название проекта или задания.
4. Все материалы ДЗ и их история коммитов создаются в ветке домашнего задания.
5. Команда открывает pull request из `homework/01-<short-name>` своего fork в ветку `seminar/01-api-scenarios` основного репозитория.
6. Для сдачи передаётся ссылка на pull request. В описании PR укажите состав команды, распределение ролей и итоговый commit.

## Дедлайн

Время указано по Москве (UTC+3).

- Soft deadline: `2026-09-21 23:59:59` — можно получить полный балл.
- Hard deadline: `2026-09-25 08:59:59` — при сдаче после soft deadline максимальный балл составляет 50% от полного балла.

Каждое следующее ДЗ продолжает это проектное решение, поэтому исправленные и согласованные материалы ДЗ 1 понадобятся в следующих работах.
