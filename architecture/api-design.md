## 2. Границы REST API
* **Внешние потребители:**
  1. **Автоматизированная банковская система (АБС)** — главный потребитель. Передает события транзакций и получает вердикт.
  2. **Команда аналитиков** — передает новые версии ML-моделей в систему.
  3. **Внешние источники данных** — предоставляют дополнительную информацию о клиенте (возраст, геолокация).
  4. **Клиент банка** — косвенный потребитель, инициирует транзакции через приложение банка.

* **Внешние системы:** 
  * АБС (Автоматизированная банковская система) — источник транзакций.
  * Внешние источники данных (Online-витрина) — поставщики данных о клиенте.

* **Проектируемые сервисы (из контейнерной диаграммы):**
  * Точка входа (Gateway) — прием событий.
  * Дополнение данных (Enrichment) — обогащение данных о клиенте.
  * Статистика клиента (Features) — агрегация данных.
  * ML-сервис — инференс модели.
  * Решение (Rules) — вынесение вердикта 1/0.
  * Загрузчик ETL — сохранение истории в ClickHouse.
  * Очередь событий (Kafka) — асинхронная обработка.

## 3. Взаимодействие сервисов
* **Внутренние взаимодействия (REST):**
  * **АБС -> Точка входа (Gateway):** Отправляет событие транзакции (JSON), получает вердикт (1/0).
  * **Точка входа -> Дополнение данных (Enrichment):** Передает данные для обогащения.
  * **Дополнение данных -> Статистика клиента (Features):** Запрашивает агрегированные данные по клиенту.
  * **Статистика клиента -> ML-сервис:** Передает признаки для инференса модели.
  * **ML-сервис -> Решение (Rules):** Передает результат предсказания для финального вердикта.
  * **Решение -> АБС:** Возвращает итоговый вердикт (1 — подтверждено, 0 — отклонено).

* **Внешние взаимодействия:**
  * Система обращается к **Внешним источникам данных** (для получения сведений о клиенте).
  * Система получает **новые версии ML-моделей** от команды аналитиков.

## 4. Обоснование методов и путей
* Мы используем **GET** для чтения данных (получение статуса, истории, статистики клиента), потому что это не меняет состояние системы.
* Мы используем **POST** для создания новых сущностей (например, отправка транзакции на проверку), потому что это изменяет состояние и требует тела запроса.
* Пути (paths) строятся по принципу `/ресурс/идентификатор`, например `/api/v1/transactions/check`.

## 5. Обработка ошибок
* Единый формат ошибки: `{ "code": 400, "message": "Описание ошибки" }`
* **400 Bad Request:** Неверный формат входных данных (некорректный JSON, отсутствуют обязательные поля).
* **404 Not Found:** Запрашиваемый объект (транзакция, клиент) не найден.
* **500 Internal Server Error:** Ошибка на стороне сервиса (например, падение ML-модели).
* **503 Service Unavailable:** Внешний сервис (например, Online-витрина или источники данных) недоступен.

## 6. Особенности кейса (Ограничения)
* **Время ответа:** Ответ от Антифрод-системы в АБС должен быть не более **100 мс** (жесткое требование для онлайн-проверки).
* **Особенности данных:** В Redis (кэш) заранее загружена готовая статистика по клиенту для мгновенного доступа.
* **Синхронность/Асинхронность:** Основной поток проверки — синхронный (чтобы уложиться в 100 мс), а сохранение истории транзакций через Kafka и ETL — асинхронное, чтобы не блокировать процесс.
