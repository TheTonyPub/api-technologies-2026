## REST-взаимодействия — кто, что, кому передаёт

### 1–3, 9. Основной API-сервис (`contracts/api/openapi.yaml`)

- **Web UI → API.** Инженер входит по email/паролю (`POST /auth/login`), получает Bearer-токен; дальше через API читает/создаёт/меняет ИС (`/information-systems`) и серверы (`/servers`), задаёт пороги (`/servers/{serverId}/thresholds`), смотрит текущее состояние (`/servers/{serverId}/current-state`), историю метрик (`/servers/{serverId}/metrics`) и прогнозы (`/servers/{serverId}/forecasts`).
- **Ситуационный центр → API.** Использует те же операции чтения состояния/сводки, что и Web UI (авторизуется отдельным сервисным токеном), в первую очередь `GET /information-systems/{isId}/summary` — агрегированную сводку по всей ИС для своего дашборда — и `GET /servers/{serverId}/current-state` / `forecasts` точечно.
- **API → Data Store.** Не REST (SQL), не описывается контрактом — упомянуто в перечне для полноты картины связей с C4-диаграммой.

### 2. Приём метрик (`contracts/metrics-collector/openapi.yaml`)

- **Агент мониторинга на сервере ИС → Metrics Collector.** Раз в минуту вызывает `POST /v1/metrics` с сырыми показателями CPU/RAM/диска конкретного сервера; аутентифицируется статическим ключом агента.

### 4. Ситуационный центр ↔ API — потоковые обновления (не REST)

Не описывается в OpenAPI, так как это WebSocket, а не REST-операция (см. правило задания «взаимодействия по gRPC можно описать словами» — применяем ту же логику к WebSocket, поскольку OpenAPI 3.2.1 описывает только REST). Словами: ситуационный центр открывает WebSocket-соединение с `wss://api.capacityforecast.example.com/v1/realtime` при загрузке дашборда (дашборд реализован на **Grafana**, канал — через **Grafana Live**), передавая тот же Bearer-токен в качестве query-параметра при апгрейде соединения. API рассылает всем подключённым клиентам JSON-сообщение вида `{ "serverId": "...", "currentState": {...}, "forecast1d": {...} }` при каждом обновлении состояния или прогноза — не реже раза в минуту, синхронно с обновлением NRT-фич в Hot Store. Первичное состояние при подключении дашборд получает REST-запросом (`GET /information-systems/{isId}/summary`), а дальше живёт на потоковых обновлениях.

### 12. Alert Worker → Каналы уведомлений (внешний REST API)

Внешний, реальный публичный сервис — контракт не пишем свой, а ссылаемся на официальную документацию поставщика, как разрешает задание:

- **Email:** SendGrid API v3, операция Mail Send — https://docs.sendgrid.com/api-reference/mail-send/mail-send
- **Push:** Firebase Cloud Messaging HTTP v1 API, `projects.messages.send` — https://firebase.google.com/docs/cloud-messaging/http-server-ref/rest/v1/projects.messages/send

Alert Worker формирует тело запроса под конкретного провайдера (адрес получателя/токен устройства берутся из профиля инженера) и вызывает соответствующий REST-эндпоинт провайдера при срабатывании алерта. Это учебный выбор конкретных провайдеров для примера — реальная интеграция может использовать любой сервис с похожим REST API.

## Ограничения по времени ответа, объёму и свежести данных

Эти ограничения — проектные требования, не измеренные и не доказанные на этом этапе (реализации ещё нет).

- **Время ответа.** Все операции чтения основного API (`current-state`, `metrics`, `forecasts`, `summary`) — целевое время ответа **до 1 секунды**, согласно требованию кейса. Приём метрики (`POST /v1/metrics`) — асинхронный (202 Accepted), собственного SLA на конец полной цепочки обработки не даём: только приём в очередь должен быть быстрым (доли секунды).
- **Объём.** История метрик хранится с исходной минутной гранулярностью до года на сервер — это до ~525 600 точек на сервер в год, поэтому `GET /servers/{serverId}/metrics` обязателен к использованию с параметрами `resolution` (агрегация) и `cursor`/`limit` (постраничный обход); без агрегации на длинный период ответ был бы неприемлемо большим.
- **Свежесть данных.** Сбор метрик — раз в минуту (`POST /v1/metrics`). Текущее состояние (`current-state`) считается свежим, если ему не больше 2 минут (удвоенный интервал сбора); более старые данные всё равно возвращаются, но с флагом `stale=true`, вместо ошибки — потребителю (дашборду) виднее, как это показать пользователю. Прогноз на 1 день пересчитывается вместе с обновлением NRT-фич (минутный цикл через Flink); прогнозы на 1 месяц/6 месяцев/1 год — батчем не чаще раза в сутки. Если прогноз для сервера/горизонта ещё ни разу не рассчитывался, API возвращает `200 OK` с `status: "pending"` вместо ошибки 404 — это осознанное решение: клиенту нужно корректно показать состояние ожидания, а не обрабатывать это как сбой.

## Обоснование границ API и принятые допущения

- **Один основной API-сервис, а не несколько.** У системы всего два внешних потребителя (Web UI и ситуационный центр) с пересекающимися потребностями (чтение состояния/прогнозов) — разделение на несколько API увеличило бы сложность интеграции без выигрыша на этом масштабе (то же решение, что и в ДЗ 1 при обосновании единого API-сервиса).
- **Отдельный API у Metrics Collector**, а не общий с основным API — потому что у него принципиально другая модель потребления (тысячи внешних агентов, асинхронная запись, другая аутентификация по статическому ключу устройства, а не по пользовательскому Bearer-токену) и другой владелец на диаграмме.
- **`/information-systems/{isId}/summary` добавлен сверх исходного набора сущностей** — это не «лишний CRUD», а прямое следствие требования кейса о dashboard ситуационного центра, показывающем состояние по ИС, а не только по отдельному серверу.
- **История метрик с пагинацией и агрегацией — не излишество**, а прямое следствие требования хранить метрики минимум за год с минутной гранулярностью (иначе ответ по одному серверу за год был бы неприемлемо большим).
- **`PUT` для порогов, а не `PATCH`** — пороги (`cpuPercent`/`ramPercent`/`diskPercent`) всегда задаются одним набором сразу (инженер настраивает все три вместе), частичное обновление отдельных полей не было бы осмысленным сценарием использования.
- **Чтение (`GET`) нигде не меняет бизнес-состояние** — в частности, `GET /servers/{serverId}/current-state` и `/forecasts` только читают уже посчитанные данные из Hot Store/Data Store, не запускают расчёт «по требованию» (расчёт всегда асинхронный, на стороне Forecast Worker/Stream Processor).
- **Длительных операций (запуск → статус → результат) в этом API нет** — единственная потенциально «длительная» операция, расчёт прогноза, всегда выполняется асинхронно фоновым воркером независимо от вызовов API; сам API только читает уже готовый (или ещё не готовый — `status: pending`) результат, поэтому паттерн «запуск/статус/результат» здесь не нужен.
- **Аутентификация — Bearer-токен (JWT)** для основного API и статический API-ключ для Metrics Collector — выбраны как самый простой вариант, покрывающий два разных сценария (пользователь vs. устройство-агент); реализация выдачи и ротации токенов вне рамок этого ДЗ.
